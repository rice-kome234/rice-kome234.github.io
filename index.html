About

自己紹介

C++によるソフトウェア開発を継続して行っています。 近年はSDF（Signed Distance Field）やデータ指向設計、メモリ管理、SIMD最適化などの技術に関心を持ち、 実装と検証を通じて理解を深めています。

将来的なチーム開発を意識し、拡張性や可読性を重視したフレームワークの設計にも取り組んでいます。 開発時には、Markdownを用いたドキュメント作成を行い、コードだけでなく設計意図や利用方法を共有しやすい環境づくりを意識しています。

新しい技術に触れた際は、単に利用するだけでなく、自ら実装しながら内部の仕組みを理解することを大切にしています。 課題に対して試行錯誤を繰り返し、より良い設計や実装方法を探究し続ける姿勢が強みです。

自分やチームが使いやすくなる小さなツールやライブラリを作ることが好きです。 よく使う処理を再利用しやすい形に整理し、他のコードから扱いやすいインターフェースとして提供できる設計を意識しています。

C++では、K&Rスタイル(カーネルスタイル)のシンプルで読みやすいコードが好きで、可読性を意識した実装を心掛けています。 コメントはDoxygen形式を意識し、.h は 公開APIの役割や使い方が分かりやすく伝わる構成を大切にしています。

01

SIMD Expression API Library

複数のfloat配列に対する要素ごとの計算を、x = a * b + c のような式APIとして書けるC++ライブラリです。 利用側は公開APIの simd.h とビルド済みの simd.lib を使う想定で、実装は simd.cpp と内部ヘッダーへ分離しています。

rice::simd::Array が配列データを持ち、rice::simd::Engine が積まれた式を execute() でまとめて実行します。 共通部分式を持つ計算やVector3更新を対象に、式として書ける分かりやすさと手書きSIMDに近い速度の両立を目指して改善を続けています。

Design Story

SIMDライブラリの設計背景

DirectXMathを使う中で、数値を毎回変換して関数へ渡す手間や、__m256 でVector3を扱うと余ったレーンが無駄になる点が気になったことから開発を始めました。

SoAへの着想

Data Layout

メモリを無駄にしない方法を考える中で、学習していたArchetype ECSから着想を得ました。 Vector3をそのまま並べるのではなく、x、y、zのように成分ごとの配列として持つSoA構造にすれば、SIMDでもデータを無駄なく扱いやすいと考えました。

Expression Templateからの見直し

Trade-off

途中ではExpression Templateで式を表現する設計も試しましたが、コンパイル時間の肥大化や管理コストが重くなり、扱いやすいものにはなりませんでした。 そこで、式そのものをデータとして持ち、後からコンパイルして実行する現在の構想へ変更しました。

Benchmark

SIMDライブラリのベンチマーク比較

SIMD-library を13th Gen Intel(R) Core(TM) i7-13650HX環境でRelease x64 / AVX2ビルドし、要素数16,777,216、繰り返し100回で5回測定した平均値です。 SIMDなしの通常ループを基準に、手書きSIMDと式APIがどの程度近い速度で動作するかを比較しています。

計算式: x/y/z = a * b + c/d/e の比較

式APIと手書きSIMD
実装 時間 通常ループ比
SIMDなしの通常ループ 3604.90 ms 1.00x
手書きSIMD 3170.54 ms 1.14x
式API 3213.46 ms 1.12x

この計算では式APIが手書きSIMDにかなり近い速度で動作しており、共有部分式を持つ式をそのまま書ける点を重視しています。

Vector3での位置・速度更新の比較

SoAベースの更新処理
実装 時間 通常ループ比
SIMDなしの通常ループ 5730.02 ms 1.00x
手書きSIMD 4692.32 ms 1.22x
式API 4641.20 ms 1.23x

SoAでデータをそれぞれ分けて持つことで、Vector3更新でも手書きSIMDに近い速度を目指しています。
